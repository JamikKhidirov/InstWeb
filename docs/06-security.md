# 06. Безопасность

Коротко: что проект делает, чего не делает и что нужно проверить перед публикацией.

---

## 1. Что хранится и где

| Данные | Где | Как защищены |
|---|---|---|
| Email, username | `server/data/users.json` | файл с правами `600`, вне git |
| Пароль | только хеш bcrypt (cost 12) | необратим, в открытом виде не хранится |
| Сессия | JWT в `localStorage` браузера | подпись `JWT_SECRET`, срок 7 дней |
| IP, браузер, время входа | сообщение в Telegram | уходит в ваш чат, не в БД |
| Токен бота | `server/.env` | права `600`, вне git |

Пароль **не** пишется в логи, **не** попадает в Telegram и **не** возвращается фронтенду.

---

## 2. Что уже сделано в коде

- **bcrypt, cost 12** — медленное хеширование, устойчиво к перебору.
- **Одинаковый ответ на неверный логин** + сравнение с фиктивным хешем — нельзя определить, существует ли аккаунт.
- **Rate limit** 30 запросов / 15 минут на `/api/auth/*` с одного IP.
- **JWT** с подписью и сроком; при смене `JWT_SECRET` все сессии инвалидируются.
- **Helmet** — базовые security-заголовки.
- **Лимит тела запроса** 16 КБ.
- **Валидация** email, username (3–30 символов, латиница/цифры/точка/`_`), пароль ≥ 8.
- **nginx**: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`.
- **`trust proxy`** включается только явно (`TRUST_PROXY=true`), чтобы нельзя было подделать IP.
- **systemd-песочница**: `NoNewPrivileges`, `ProtectSystem=strict`, запись только в `server/data`.
- **Экранирование HTML** в сообщениях Telegram.

## 3. Чек-лист перед публикацией

### Обязательно

- [ ] `JWT_SECRET` — случайные 32+ байта (`openssl rand -hex 32`), не `dev-only-insecure-secret`.
- [ ] `NODE_ENV=production` на сервере.
- [ ] HTTPS работает, HTTP редиректит на HTTPS.
- [ ] `server/.env` — права `600`, не в git (`git status` чистый).
- [ ] Токен Telegram не засветился в GitHub/скриншотах.
- [ ] `TRUST_PROXY=true` только если сервер реально за nginx.
- [ ] Firewall: открыты 22, 80, 443; 4000 — только локально.
- [ ] Бэкап `users.json` настроен.
- [ ] Пароли пользователей не появляются в логах (`journalctl | grep -i password` → пусто).

### Желательно

- [ ] Отключён вход по паролю SSH, root-логин запрещён.
- [ ] `fail2ban` для SSH.
- [ ] HSTS (после стабильного HTTPS).
- [ ] Отдельный бот/чат для уведомлений.
- [ ] Мониторинг (`uptime-kuma`, healthchecks).
- [ ] Регулярные обновления: `sudo apt update && sudo apt upgrade`.

## 4. Ограничения демо-версии

Это учебный проект, а не готовый продакшен-аутентификатор:

- **JSON-файл вместо БД.** Нет транзакций и конкурентного доступа; при росте нагрузки возможны гонки. Для реального проекта — PostgreSQL + уникальные индексы на `email`/`username`.
- **Нет подтверждения email** — можно зарегистрировать чужой адрес.
- **Нет сброса пароля и 2FA.**
- **JWT в `localStorage`** уязвим к XSS. Альтернатива — httpOnly-cookie + CSRF-токен.
- **Нет блокировки аккаунта** после N неверных попыток (есть только лимит по IP).
- **Нет аудита действий** и уведомлений о подозрительных входах.
- **Нет проверки сложности пароля** кроме длины.
- **IP-геолокация** (если включена) отправляет IP на сторонний сервис `ip-api.com`.

Если проект вырастет — начните с БД, httpOnly-cookie и подтверждения email.

## 5. Если что-то утекло

| Что утекло | Действия |
|---|---|
| `TELEGRAM_BOT_TOKEN` | BotFather → `/revoke` → новый токен в `.env` → restart |
| `JWT_SECRET` | новый секрет в `.env` → restart (все сессии сброшены) |
| `.env` целиком в git | удалить из истории (см. [07-github.md](07-github.md)), перевыпустить все секреты |
| `users.json` | сменить пароли пользователей, уведомить их, проверить логи |
| Доступ к серверу | сменить пароли/ключи, переустановить систему при подозрении на руткит |

После любого инцидента: проверить `auth.log`, `journalctl`, список процессов, cron, authorized_keys.

## 6. Юридическая сторона

- Нельзя использовать чужие логотипы, название и фирменный стиль, выдавая свой сайт за чужой сервис.
- Нельзя собирать пароли от чужих аккаунтов — это квалифицируется как неправомерный доступ к компьютерной информации (ст. 272 УК РФ и аналоги в других странах).
- Учебные имитации допустимы, если они явно помечены, не собирают реальные секреты и проводятся с согласия участников.
- Публикуя сайт, вы отвечаете за обработку персональных данных (email, IP): нужна политика конфиденциальности и законное основание.

Этот проект специально сделан так, чтобы не нарушать эти правила: свой бренд, свои аккаунты, никакой пересылки паролей.

## 7. Полезные команды аудита

```bash
# кто слушает порты
sudo ss -tlnp

# права на .env
ls -l /var/www/pixora/server/.env      # -rw------- 

# не закоммичены ли секреты
cd /var/www/pixora && git log --all --full-history -- server/.env

# ошибки авторизации в nginx
sudo grep -i ' 401 \| 429 ' /var/log/nginx/access.log | tail

# последние входы в систему
last -n 20
```
